## 2026-10-09 — 從構想到 M1 上機

### 1. 找路線：RP2040 上做 SDR 有哪幾種做法

上網查了現有的做法，歸成三類：

| 做法 | 代表作 | 外加硬體 | 收訊範圍 |
| :--- | :--- | :--- | :--- |
| Tayloe 正交取樣混頻 | Pi Pico Rx（Jon Dawson） | 類比開關＋運放 | 約 30 MHz（長、中、短波） |
| 直接取樣 | PiccoloSDR | 幾乎沒有 | 0–250 kHz（只有 LF） |
| QSD/QSE 收發機 | uSDR-pico | Si5351＋濾波＋放大 | HF，可發射 |

Pi Pico Rx 最適合這台掌機，但要做子板。使用者問「有沒有不加硬體的」，於是先走
**直接取樣**：只能收 LF，但可以先把取樣、FFT、瀑布圖、按鍵、UI 整套架構做起來，
之後換成 Tayloe 子板時，DSP 與 UI 都能沿用。

### 2. 「只接一根天線」行不通，要 3 顆零件

本來以為接一根電線就好。仔細看了接腳之後發現三個問題：

1. **ADC 需要偏壓**：0–3.3 V 的 ADC 量不到在 0 V 上下擺的 µV 級訊號，負半週還會被
   ESD 二極體削掉。晶片內建的上下拉做不到中點（兩個一起開會變 bus keeper）。
2. **GPIO 27 不能用**：它接 74HC165 的 QH，是一直在推的推挽輸出。
3. **GPIO 26 是鍵盤的 CLOCK**：改當 ADC 時 74HC595/165 的時脈輸入會浮動。

第一版設計把偏壓放在中點 1.65 V，然後才發現**那正好是 74HC 的切換門檻**——595/165
會亂移位、產生穿透電流、把數位雜訊灌回訊號。改成 **0.41 V**（330k/47k 分壓）：
低於 74HC 的 V<sub>IL</sub>，CLOCK 在取樣期間穩穩是 LOW；而天線訊號只有 µV–mV，
0.41 V 的餘裕綽綽有餘。1 nF 耦合電容同時當 3.9 kHz 高通，擋掉 60 Hz 交流聲。

> **教訓**：偏壓不一定要在中點。訊號很小時，偏壓的位置應該由「這條線上還有誰」決定。

### 3. 分時：ADC 與鍵盤輪流用 GPIO 26

```
|── ADC 取樣 32768 點 (65.5 ms) ──|掃鍵盤 ~1ms|── ADC 取樣 ──|…
```

- LATCH 的接法原本列為待確認。讀 PicoApple2 的 `scan_matrix()` 時序後確認：
  **595 的 RCLK 與 165 的 SH/LD 共用 GPIO 14**（拉高鎖存 595，拉低 1 µs 讓 165 載入）。
  取樣期間 LATCH 停在高，595 的輸出凍結，LED 不閃。
- `keys.c`（取自 retro-dict）的 30 ms 去彈跳**不用改**：在 65 ms 的掃描週期下，
  它本來就等於「連續兩次一致」。
- 鍵盤矩陣上**已經沒有方向鍵**（retro-dict 的 HANDOVER 記載），方向改走 D-pad。
- CLOCK 線上多了 1 nF 與天線，掃描時脈放慢到約 125 kHz，驅動能力開到 12 mA。

### 4. 程式結構：照 retro-dict 的分層

- `firmware/`：純 C，**不知道板子存在**。FFT、頻譜、瀑布圖、狀態機、逐列畫面、字型。
- `RetroSDR/RetroSDR.ino`：只有硬體膠水（ADC DMA、GPIO 26 分時、掃鍵盤、LCD DMA）。
- `RetroSDR/src/rs_*.c`：一行的轉接檔，因為 Arduino 會把 sketch 複製到別處編譯。

好處是整條訊號路徑能在 PC 上用合成訊號驗證（`firmware/test_pc.c`），
連畫面都能輸出成 PPM 給人看。

### 5. PC 驗證時抓到的兩件事

**q15 每級除 2 會量不到雜訊。** 12 位元 ADC 的雜訊只有幾個 LSB，4096 點 FFT 每級
>>1 等於除以 4096，雜訊被截成 0。改成**區塊浮點**：只在快溢位時才右移，記下次數，
換算 dB 時補回去。

**蝴蝶運算的 `>>15` 一律往下截斷**，在 bin 5 留下一根 -62 dBFS 的假訊號。
加上四捨五入（`+ 0x4000`）後降到 -71 dBFS，接近 12 位元 ADC 本身的極限。

PC 測試結果：滿刻度正弦 0.1 dBFS；雜訊底線 -90 dBFS/bin（理論 -88.5）；
只有 3 LSB 的 BPC 載波仍高出雜訊 33 dB。

字型是自己畫的 5×7，用字元畫（`'#'`）存，比十六進位好校對。

### 6. 工具鏈：這台電腦沒有

其他專案的編譯腳本會**在編譯當下**去找工具鏈（PicoApple2 的 `scan_env.ps1`），
不是寫死路徑，所以「其他專案知道」不代表這台有。搜過整顆 C 槽確認沒有之後安裝：

- Arduino IDE 2.3.10（winget，裝在使用者目錄 `%LOCALAPPDATA%\Programs\arduino-ide`）
- arduino-pico **5.6.1**（照 retro-dict HANDOVER 固定版本，不用最新的 6.3.0）
- arduino-cli 加進使用者 PATH

第一次編譯就成功：flash 80 KB，RAM 85%。

### 7. 燒錄：保留 loader 相容性

用 USB 直接燒一般版會蓋掉 flash 開頭 16 KB 的 loader。改做 standalone 版：
從 rp2040-handheld-bundle 的 Release 下載現成的 `trampoline.uf2`，
用 loader repo 的 `merge_uf2.py` 合併。

之後重燒用 arduino-pico 的 **1200 baud 觸發**讓板子自己進 BOOTSEL，不用按鈕。

### 8. 上機：CPU 不夠，拆開來看

第一次上機：**每塊 139 ms，一塊只有 65 ms**，每一塊都掉。M1 能動、畫面正確，
但只有每秒 7 塊。

加了逐段計時之後，問題一個一個浮出來：

| 步驟 | 每塊時間 | DROP | 發現 |
| :--- | ---: | :--- | :--- |
| 初版 | 139 ms | 全掉 | |
| 超頻 250 MHz | 124 ms | 全掉 | 預設原本就是 200 MHz，不是以為的 133 MHz，只快了一點 |
| clk_peri 改接 clk_sys | 84 ms | 全掉 | **SPI 實際只有 24 MHz**，畫面 61 → 23 ms |
| FFT 放 RAM＋-O3 | 84 ms | 全掉 | 幾乎沒用 |
| **實數 FFT** | **60 ms** | **0** | FFT 52 → 24 ms |

**SPI 只有 24 MHz**：arduino-pico 把 clk_peri 接在 48 MHz 的 USB PLL 上，
SPI 最快 clk_peri/2 = 24 MHz。程式裡寫的 `spi_set_baudrate(62500000)` 拿不到，
而且**不會報錯**。改用 `clock_configure()` 把 clk_peri 接到 250 MHz 的 clk_sys。

> 這是 **arduino-pico 特有**的：pico-sdk 預設 clk_peri = clk_sys，所以用 pico-sdk 編的
> rp2040-infones 跑 40 MHz 沒問題（使用者確認）。生態系裡同樣用 arduino-pico 的
> PicoApple2、retro-dict 是否也被卡在 24 MHz，還沒驗證；看序列埠印 `spi_get_baudrate()`
> 就知道。

**-O3 和放進 RAM 沒用**：反組譯看內迴圈，每個蝴蝶約 70 條指令，那已經是 M0+
的本事。要快只能**少做**——輸入是實數，4096 點複數 FFT 有一半在算零。改成
偶數點進實部、奇數點進虛部，做 2048 點複數 FFT 再拆分，運算量減半。拆分要算 2X
（不除 2）免得丟掉最低位元，平方要 64 位元。另外加了一個鏡像測試：拆分寫錯的
典型症狀是在 M−k 冒出鏡像，實測鏡像 bin 是 -80 dBFS。

### 目前的數字（250 MHz、4 段 FFT）

```
proc 60 ms = scan 1 ms + dsp 36 ms (win 3, fft 24, db+split 8, post 1) + draw 23 ms
DROP 0 | NF -101 dBFS | RAM 82%（剩 46 KB）
```

### 還沒解決 / 下一步

- **餘裕只剩 5 ms**。M2 要在 Core 1 跑 DDC，Core 0 這邊不會變重，但要留意。
  還能挖的：dB 換算（8 ms）可以只算畫面需要的 bin、ui_line（12.6 ms）
  可以放進 RAM。
- **雜訊底線 -101 dBFS 比模擬的 -90 低 10 dB**，ADC 實際雜訊比假設小。要配合
  偏壓網路、有無天線、按 `q`（LCD 安靜）前後分別記錄才能判讀。
- 鍵盤在慢 CLOCK 下有沒有誤觸、漏鍵，還沒確認。
- M2：窄頻 DDC、CW/AM 解調、喇叭出聲。M1 本來就沒有聲音。

## 2026-10-09（續）— M2：喇叭出聲

### 1. 架構

- **Core 1** 跑 DDC：NCO 混頻 → 三階 CIC ÷64（int64 積分器）→ 127 階 FIR → 解調 → AGC。
  Core 0 每抓完一塊就把緩衝區編號丟進跨核 FIFO；那一塊在下一塊抓完前不會被覆寫。
- 四種模式共用一條鏈，只差本振位置、濾波器寬度與最後怎麼取：CW（800 Hz 嗶聲）、
  USB、LSB（取共軛翻頻）、AM（取振幅）。
- 音訊 7812.5 Hz（500 k ÷ 64，一塊 32768 點剛好 512 個）。Core 1 上的鬧鐘中斷
  每約 128 µs 寫一次 GPIO 7 的 PWM；PWM 載波 500 kHz，跟 ADC 同頻，摺疊到 DC。
- 用 `pwm_set_chan_level`（32 位元寫入）而不是 DMA：retro-dict 記載過 8 位元 DMA
  寫 PWM 暫存器只有卡答聲。

PC 測試四種模式第一次就全過；USB 對反邊帶的抑制約 62 dB。

### 2. 上機的兩個問題

**每秒約 56 次斷音。** 產出是每 66.5 ms 一次倒進一整塊，播放是等速的。
環形緩衝的目標水位只設 256，兩塊之間就見底。改成依水位在 127/128/135 µs
之間微調播放間隔，水位停在 768 以上（約 0.1 s 延遲）。

**噠噠聲，每塊一聲。** 兩個原因疊在一起：

1. 頻譜那邊有 `SDR_SKIP` 丟掉偏壓回穩的暫態，**DDC 沒丟**——每塊開頭約 500 counts
   的階躍直接灌進去，再被 AGC 放大。
2. 鍵盤掃描的約 1 ms 空檔裡，真實訊號的相位一直在走，**NCO 卻停著**，每塊都是一次
   相位跳躍。

修法：DDC 也跳過開頭 512 點；把「空檔＋跳過的點數」補進本振相位（空檔長度從
Core 0 量到的 scan_us 換算，跟著緩衝區編號一起塞進 FIFO 那個 word）；DC 改用每塊
實際平均（偏壓在 508，不是 2048）。PC 上重現上機狀況的測試：有補償時嗶聲高出雜訊
44 dB，沒補償只有 23 dB。上機確認噠噠聲消失。

> **教訓**：同一個前提（每塊開頭有暫態、塊與塊之間有空檔）要在**每一條**吃這塊
> 資料的路徑上處理。頻譜那條處理過，不代表 DDC 那條也處理過。

### 目前的數字

```
Core 0: proc 62 ms（scan 1 + dsp 37 + draw 23），DROP 0
Core 1: ddc 55 ms/block（預算 65 ms），音訊水位約 950、不再斷流
RAM 86%
```

### 還沒解決 / 下一步

- ~~Core 1 太重~~：已處理，見下一節。
- AGC 的上限（沒訊號時雜訊被放多大聲）還沒依實際聽感調。
- 還沒收到真實訊號：需要偏壓網路＋天線，或用 PIO 在 GPIO 0 自發 68.5 kHz 測試音。
- 窄頻放大的頻譜（DESIGN.md 的窄頻模式）還沒做，目前畫面仍是寬頻。

## 2026-10-09（續）— Core 1 優化：55 → 28 ms

先加計時再動手：FIR＋解調 37.5 ms、CIC 迴圈 17.8 ms。

| 步驟 | FIR＋解調 | CIC | Core 1 合計 |
| :--- | ---: | ---: | ---: |
| 起點 | 37.5 ms | 17.8 ms | 55 ms |
| FIR 對稱摺疊＋拆乘法 | 14.1 ms | 18.0 ms | 32 ms |
| CIC 拆兩級 | 14.2 ms | 14.1 ms | **28 ms** |

**FIR**：瓶頸是 64 位元乘法（M0+ 上是 `__aeabi_lmul` 函式呼叫，每塊 13 萬次）。
係數對稱 → 先把對稱兩點相加再乘，乘法減半；樣本拆高低 16 位元各做一次 32 位元
乘法（低半最大 2,147,385,345，剛好塞進 int32）。結果與 int64 直乘**逐位元相同**，
PC 測試數字一位不差。係數改成只算一半再鏡射，保證完全對稱。

**CIC**：單級 ÷64 要 44 位元只能用 int64。拆成兩級 ÷8：第一級（500 kHz）只長
9 位元，本振降到 q10 後 int32 就夠；第二級在 62.5 kHz 用 int64，次數少 8 倍。
兩級 CIC³(÷8) 串接與單級 CIC³(÷64) 的響應**數學上相同**。

但只從 18 ms 降到 14 ms，不是預估的 6 ms。反組譯看到第一級迴圈約 50 條指令，
一大半是堆疊存取：I、Q 各 3 個積分器加相位、步進、指標、計數、DC，遠多於 M0+
的 8 個低位暫存器。再拆成 I、Q 兩趟大概還能省 4–5 ms，但 28/65 ms 已經夠用，
先停在這裡。

> **教訓**：在 M0+ 上，「int64 換 int32」省下的是指令，**暫存器壓力**才是決定性的。
> 估算時要數同時活著的變數有幾個。

### 要不要改用 pico-sdk

評估過，**現在不換**：熱點是純運算，兩邊同一個 GCC；clk_peri 的差異已手動解決；
框架負擔只有每秒一行的 USB 序列埠。真正的好處是省幾 KB 到十幾 KB 的 RAM
（目前 86%），等 M4 SD 卡錄音若吃緊再換。`firmware/` 是純 C，換的時候只動 sketch。

## 2026-10-09（續）— 焊上偏壓網路，第一次實測

焊上 330k／47k／1nF 與一段電線天線（GP26 = Pico 第 31 腳，3V3(OUT) 第 36 腳，
AGND 第 33 腳）。

**鍵盤正常**：0.41 V 偏壓不干擾 74HC，「同一支腳兼當鍵盤 CLOCK 與天線輸入」在實機
上成立。

**雜訊底線 -101 → -97 dBFS**：天線確實帶進了外面的訊號與雜訊。

### GPIO 0 測試訊號

加了鍵盤 `T`：GPIO 0 用 PWM 打 68,493 Hz 方波（250 MHz ÷ 3650）。沒有偏壓網路時
板上串音量不到；焊好之後用杜邦線從 GPIO 0 靠近天線：

| | 讀數 |
| :--- | :--- |
| 68.5 kHz 基頻 | -87 到 -90 dBFS，S/N 7–11 dB，**穩定** |
| 205.5 kHz 三次諧波 | 約 -93 dBFS（方波理論上比基頻低 9.5 dB，吻合） |
| 喇叭（CW） | 800 Hz 嗶聲「不是很乾淨但聽得出來」 |

天線 → ADC → 頻譜 → DDC → 喇叭整條路徑驗證完成。

### 40 kHz 上有東西（可能是 JJY）

調在 40.000 kHz，每秒讀一次：-80 到 -95 dBFS，S/N 2–17 dB，**跳動很大**。

JJY（日本福島，40 kHz）每秒以載波強弱編碼，晚上在台灣有機會收到。同一條線上的
測試訊號量起來是穩定的 7–11 dB，40 kHz 卻大起大落——支持它是**有鍵控的訊號**
而不是穩定的本地干擾。還不是定論：要看瀑布圖有沒有每秒重複的虛線，或移到 41 kHz
看它是否消失。

### 還沒解決 / 下一步

- 嗶聲不夠乾淨：S/N 約 10 dB（183 Hz 解析頻寬下量的），AGC 把雜訊也放大。
  可以試更窄的 CW 濾波器、調 AGC 上限，或讓測試線耦合得更緊。
- 確認 40 kHz 是 JJY → M3 的授時碼解碼就有真實訊號可以驗證。

### 拔掉 USB 之後：聽得到中波廣播（混疊）

- **筆電充電器是雜訊來源**：插著充電時 S/N 明顯變差；拔掉充電線（筆電用電池、
  USB 仍接著）廣播聲就回來。收訊時讓筆電用電池跑。
- **聽得到人聲與音樂，但辨認不出內容**。0–250 kHz 在台灣沒有人聲廣播，所以這是
  **中波 AM（530–1600 kHz）摺疊進來的**：ADC 前面沒有抗混疊濾波器，而 RP2040 ADC
  的類比頻寬高於取樣率，高於 250 kHz 的訊號會依
  `f mod 500k`（大於 250k 再取 500k − 它）摺進來。例如 1080 kHz → 80 kHz。
- 最早評估「欠取樣收中波收不到能聽的東西」**是錯的**。
- 副作用：所有中波電台都摺進 LF 段，**40 kHz 那個訊號也可能是某台中波的混疊**，
  不一定是 JJY。

### 待辦：中波模式（使用者要求先記下，暫不實作）

輸入電台的**實際頻率**（例如 `1080`），韌體換算摺疊後的位置去調諧，模式自動切 AM。
要處理的：
- 換算：`a = f mod 500k；a > 250k 時 a = 500k − a`，且這時頻譜是**翻轉**的
  （AM 對稱不受影響，SSB 要交換 USB/LSB）。
- 多個電台可能摺到同一個位置，無法分開——要在畫面上提示。
- 先請使用者回報聽到廣播時的頻率，對照台灣中波電台表驗證換算。
- 收訊改善：天線拉長拉到窗外、AGND 接地線、USB 線加磁環。

## 2026-10-09（續）— M3：JJY 解碼器

### 做了什麼

- `firmware/jjy.c`：三層——包絡 → 自適應門檻與邊緣（狀態要維持 80 ms 才算數，
  高低差不到 6 dB 視為沒訊號）→ 每秒一個符號（0.2/0.5/0.8 s）→ P0+M 對齊幀 →
  解碼（標記位置、固定 0、同位、BCD 每位 ≤ 9、範圍）。漏掉的秒補「?」，幀不錯位。
  第 15、45 分鐘的呼號秒不檢查。鎖定 = 連續兩幀成功且相差一分鐘。
- 格式依 NICT 官方說明與 Wikipedia（兩者一致）：時間碼代表 M 那一刻，JST；
  載波 100% / 10%。
- DDC 加包絡輸出（每 8.2 ms 一點，AGC 之前的通帶功率），附帶**真實時間戳**：
  從 DDC 的取樣計數算，把鍵盤掃描的空檔也算進去，不然「一秒」會短 3%。
- 畫面：調在 40 / 60 kHz ±500 Hz 時，資訊列第二行顯示

## 2026-10-10 — M4：SD 卡錄音

目的：把 40 kHz 附近蓋台的大訊號錄回電腦，弄清楚它是什麼（JJY、本地干擾、
還是中波混疊）。

### 錄什麼：寬頻原始樣本，不是 DDC 後的 I/Q

| | 寬頻原始（採用） | DDC 後的 I/Q |
| :--- | :--- | :--- |
| 頻寬 | 0–250 kHz 全部 | 調諧點 ±幾 kHz |
| 資料量 | 1 MB/s（64 KB／塊） | 32 KB/s |
| 能回答的問題 | 大訊號在哪、有幾根、怎麼變、旁邊還有什麼 | 只看得到調諧點 |

要找「不知道是什麼」的訊號，寬頻才有用；I/Q 可以事後在電腦上從寬頻檔算出來
（`tools/rec_analyze.py --iq`）。

### 做法

- 鍵盤 `R` 開始／停止，最長 60 秒（約 60 MB）。檔名 `RECnnn.WAV` 自動編號。
- 剛抓好的那一塊 **原封不動** 寫進 .wav（ADC 原值 0..4095 當 16 位元，帶直流），
  趁 DMA 抓下一塊的 65 ms 裡寫完。不轉換、不另配緩衝：Core 1 也在讀同一塊，兩邊都只讀。
- 錄音時 Core 0 **不做 FFT**、畫面每秒才畫一次 —— 平常 DSP＋畫面就要 60 ms，
  再加寫卡一定掉塊。Core 1 照常跑，喇叭還有聲音。
- 檔案先 `preAllocate` 成 60 秒大小，寫的時候 FAT 不用找空間，停止時截短。
- 同名 `.TXT`：取樣率、塊大小、SKIP、調諧點、模式、寫卡平均／最大耗時、
  **每一塊的開始時間（µs）**。塊間空隙與掉塊從這裡看得出來。
- SD 用 SdFat 直接開（`SdFs`，DEDICATED_SPI，spi1 25 MHz = clk_peri 250 ÷ 10），
  第一次按 `R` 才初始化；沒插卡會顯示 `REC: NO SD CARD`（SdFat 逾時約 2 秒，那幾塊會掉）。
- 純 C 的部分：`firmware/wav.c`（檔頭）、`sdr.c` 的 `R` 鍵與狀態列。PC 測試第 [10] 組。

### 分析腳本 `tools/rec_analyze.py`

只用 numpy＋Pillow。丟掉每塊開頭 512 點暫態，16384 點分段（30.5 Hz 解析度），輸出：
最強的幾根訊號、每根強度的起伏（JJY/BPC 每秒一個符號 → 起伏在 1 Hz 附近）、
平均頻譜圖、lo–hi 瀑布圖、可選的 I/Q 立體聲 wav（50 ksps，SDR++／SDR# 能開）。

用合成檔驗證過（40 kHz 每秒開關一次＋41.5 kHz 穩定載波，格式同韌體）：
40.009 kHz 起伏 20.8 dB、在 0.94 Hz；41.504 kHz 判為 steady。

**修正過的地方**：第一版把段與段的間隔當成 nfft/fs（32.8 ms），但一塊扣掉 SKIP

### 為什麼電腦上解調 26 kHz 比掌機清楚

使用者發現：同一個 1026 kHz 混疊，從錄音在電腦上解調，比掌機喇叭清楚。
先排除畫面：按 `q` 停掉 LCD，聲音沒有差別。

方法：寫了一支 PC 小程式，把 REC001 餵給掌機的 `ddc.c`，輸出掌機會播的音訊，
和 numpy 解調的版本比。指標是頻譜各段的能量比例、峰值／均方根、
每 100 ms 音量的 90/10 百分位差（「起伏」）。

| | 50–300 Hz | 0.3–1 kHz | 1–3 kHz | 3–4.5 kHz | 峰值／均方根 | 起伏 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 原本的 `ddc.c`（7812.5 Hz，AM 6 kHz） | 35% | 31% | 33% | **0%** | **3.6** | 4.0 dB |
| ＋載波 AGC | 41% | 30% | 29% | 0% | 6.2 | 7.2 dB |
| ＋音訊 15625 Hz（AM 8 kHz） | 30% | 23% | 34% | 13% | 5.7 | 6.6 dB |
| 電腦 numpy 解調（參考） | 25% | 20% | 34% | 19% | 6.0 | 6.3 dB |

找到三個原因：

1. **AGC 把動態壓扁**：原本對解調後的音訊做峰值 AGC（快攻、0.5 s 放），
   字與字之間的停頓被拉高、下一個字又被壓下去。
   改成 **AM 依載波（`am_dc`）定增益**，再加一個只在快削頂才動作的限幅器。
   - 只依載波、沒有限幅時，沒電台的頻率雜訊大 12 dB、削頂 4.7%（沒載波時雜訊
     等於 100% 調變）。量了 `am_dc`：沒電台約 15000、1026 kHz 約 106000，
     載波下限 `AM_FLOOR` 設 60000，加限幅 30000 之後不削頂。
   - 代價：沒電台時的雜訊比舊版大約 2 dB，和電台音量差不多。
   - CW／SSB 沒有載波，維持峰值 AGC。
2. **音訊頻寬只有 3 kHz**：7812.5 Hz 取樣、AM 通帶 ±3 kHz，子音被切掉。
3. **CIC 的衰減沒補償**：兩級 CIC 總共 ÷64，第一個零點在 7812.5 Hz，
   **3 kHz 已經掉 6.7 dB**，FIR 是一般的低通，沒有補。

2 和 3 一起解：第二級 CIC 從 ÷8 改成 ÷4，音訊 15625 Hz，零點移到 15625 Hz，
3 kHz 只掉 1.6 dB。AM 通帶改成 8000／6000／4000，預設 8000。跟著改的：
`CIC_SHIFT` 12 → 9、AGC 與 AM 去 DC 的係數（每秒樣本數加倍，時間常數不變）、
`DDC_ENV_DECIM` 64 → 128（JJY 包絡維持 122 Hz）、播放間隔 128 → 64 µs、
`AUD_N` 2048 → 4096、水位門檻 768/1280 → 1536/2560。

上機實測：

| | 7812.5 Hz | 15625 Hz |
| :--- | ---: | ---: |
| Core 1 每塊 | 31 ms | **47 ms**（預估 46） |
| 其中 FIR＋解調 | 15 ms | 31 ms |
| RAM 剩下 | 24.8 KB | 19.5 KB |

- Core 0 不變，每塊 62 ms、不掉塊。音訊水位穩定在約 1815，開機後見底次數不再增加。
- Core 1 只剩約 18 ms 餘裕，之後要在 Core 1 加東西會很緊。
- FIR 仍是 127 階，過渡帶從約 200 Hz 變約 400 Hz：CW 250 Hz 檔實際會寬一些，PC 測試沒有測這檔。
- 使用者試聽：新 AGC「有清楚一點點」；改 15625 Hz 之後的掌機喇叭還是不如電腦。

### 喇叭與地線

- **用耳機聽比喇叭清楚很多**：同一個 PWM 訊號，差別只在 PAM8403＋小喇叭這段。
  剩下的音質差距主要在喇叭，軟體能做的有限（頂多加一點人聲頻段的提升）。

## 2026-10-10（續）— 音高會飄：改成固定 64 µs 播放

使用者發現：電腦解調同一段錄音正常，掌機上語音的音高會飄。使用者猜是 LCD 的 DMA 干擾
Core 1，問改用 PIO 能不能改善。

**原因不是 DMA，也不是 PIO 能解決的**：`audioTick()` 依水位在 63／64／68 µs 之間換速度。
DDC 每 66.493 ms 只產出 1008 個（約 15160 Hz，塊與塊之間的掃描空檔沒有樣本），
三檔沒有一檔等於它，播放速率每約 2 秒在 +3% 和 −3% 之間切換，音高跟著飄半個半音左右。
DMA 搶匯流排頂多讓中斷晚幾百 ns，不改平均速率。

**改法**（DESIGN.md §4.3）：
1. DDC 把 gap ＋ skip 換算成音訊樣本，在輸出開頭線性內插補上（最多 `DDC_FILL_MAX` = 64），
   BFO 相位跟著走。每塊約 1039 個，平均剛好 15625 Hz。ADC 和計時器同一顆石英，不會越差越多
2. 播放固定 64 µs。先存到 1536 才開播；水位漂出 256–3328 才丟／重複一個樣本（統計頁 `slip`），
   見底就重新存（`under`）
3. gap 由 µs 換算點數時改成四捨五入

代價：補進去的約 2 ms 是直線，test_pc [6] CW 跨塊純度 42.5 → 30.7 dB（門檻 25）。
新增測試：20 塊含空檔產出 20780 個，跟理論值完全相同。

**插曲**：第一次「改善但還有一點飄」是在**舊韌體**上聽的（統計頁還是 `underruns`，沒有 `slip`）——
SD loader 可能已被蓋掉，開機直接進舊程式，卡上的 standalone uf2 沒用到。改成直燒
`build/RetroSDR.ino.uf2` 之後才是真正的新版。教訓：上機前先看統計頁的格式確認版本。

**上機實測**：音高不飄，`under` 0，`slip` 一分鐘不增加。

## 2026-10-10（續）— 聲音電路（D 類功放）濾波分析

看電路圖「聲音」頁，對照韌體設定。

**實裝值**（圖上有斜線的零件都裝第一組值）：R3 NC、R4 0 Ω、R5 0 Ω、R6/R7 12k、C4/C5 100 nF、
R8 NC、C7 1 µF。功放是 HT6872。

**路徑**：SND_P7（GPIO7 PWM）→ R2 270 Ω ＋ C1 100 nF 一階低通（fc ≈ 5.9 kHz）→ R4 0 Ω（R3 沒裝，
所以沒有分壓）→ RV1 10k 雙聯音量 → J3 耳機孔。RV1 對 C1 節點的負載是 10k 對 270 Ω，只損失約 3%。
耳機孔的常閉接點把訊號送進功放，插耳機時喇叭自動斷開。HT6872 接成單端輸入：IN− 接訊號，
IN+ 經 C4/R6 再經 R5 0 Ω 接地，兩腳阻抗對稱。輸入高通 100 nF/12k ≈ 133 Hz。輸出沒有 LC 濾波
（filterless），直接接喇叭。

**PWM 載波**：clk_sys 250 MHz ÷（`PWM_WRAP` 499 ＋ 1）＝ **500 kHz**，約 9 bit。一階 RC 在
500 kHz 衰減約 38.6 dB，3.3 V 方波的基波（約 2.1 V 峰值）剩約 25 mV，再經音量電位器衰減。
結論：一階就夠，不用急著加第二節。5.9 kHz 截止對 AM/SSB 語音（3–4 kHz）剛好。

**待確認／注意**：
- HT6872 自己的開關頻率也在幾百 kHz。如果接近 500 kHz，差頻可能落進音頻。驗證方法：送
  `PWM_MID` 靜音、音量開大聽有沒有嘯聲。有的話在 IN− 前加 1k ＋ 1 nF（約 160 kHz）。
- 500 kHz 和它的諧波（1、1.5 MHz…）落在中波。收 MW 時，如果瀑布圖在整數倍位置出現固定突波，
  先懷疑 PWM 走線和喇叭線的輻射。必要時在 OUT± 各串鐵氧體磁珠，再各加約 1 nF 到地。
- R8 沒裝，所以 SD 完全由 GPIO 控制，不會有 VSYS 往 GPIO 倒灌的問題。以後要裝上拉的話，
  要接 3V3，不能接 VSYS。
- VDD 只有 C6 1 µF，建議靠近 pin 6 再加 10 µF，減少電源雜訊干擾 RF/ADC。
- R8 沒裝，SD 腳完全靠 GPIO。開機到韌體設定 EN 之前這支腳是浮接的，功放可能隨機被開啟，開機時發出
  「啵」聲。如果有聽到開機爆音，在 SD 腳加一顆下拉電阻（例如 100k）接地，讓功放預設關閉，等韌體
  再打開。

## 2026-10-10（續）— S 表（通帶內 S/N）

DESIGN §11 第 10 項。原本的 S/N 是單一 bin 對全頻段中位數，跟耳朵聽到的差很多（AM 通帶約 65 格）。

**做法**（DESIGN §3.1）：從寬頻頻譜算，放在 Core 0 的 `sdr_band_meter()`，不碰只剩 17 ms 的 Core 1。
通帶跟 `ddc_set` 一致；雜訊取兩側各 max(通帶, 16 格) 的中位數；BAND = 通帶線性功率加總 ÷（中位數 × 格數）。
畫面：資訊列第一行加綠色 `BAND xx.x dB`，兩行字中間一條 3 px 長條（60 dB 滿格）。SIG／S/N 與 JJY 記錄的 `sn=` 不動。

**第一版測試沒過**：CW 500 只有雜訊時讀 4.6 dB。另寫小程式跑 60 塊：平均 0.2 dB（無偏），
是單塊起伏大（CW 約 5 格，標準差 1.7 dB），測試剛好抽到一塊偏高的。加 1/4 指數平均（約 0.27 s），
換通帶就重來；起伏降到 0.5 dB。test_pc [13]：沒訊號約 0、CW 與 AM 差約 11 dB、USB 只看上邊帶。

`powf` 換成查表；比較用的暫存陣列從 2048 B 縮到 512 B（放在堆疊）。

**上機**：Core 0 每塊 62 → 63 ms（dsp 37 → 38），比估計的 0.5 ms 多；不掉塊，Core 1 不變。
使用者確認 S 表正常。Core 0 只剩約 2.5 ms，之後要加東西得先找地方省。

## 2026-10-10（續）— BPC 解碼

BPC 是中國的長波授時台（68.5 kHz，河南商丘，國家授時中心，90 kW），開機預設就調在它。

**格式**：官方沒有公開。Wikipedia 的 BPC 條目有整體格式，但抓下來的表格部分錯亂（星期的位置、同位涵蓋範圍）；
[libdriver/bpc](https://github.com/libdriver/bpc) 是實際能用的解碼器，照它的解析順序補齊，兩者一致。
（原本想參考 hzeller/txtempus，查了才發現它沒有 BPC。）要點：每秒開頭降到 10%，0.1–0.4 s = 0–3；
20 秒一幀、P0 整秒不降；時 12 小時制＋下午旗標；兩個偶同位（P10、P19 的低位）。表見 DESIGN §5。

**實作**：`firmware/bpc.c`，結構照 jjy.c 三層。差別在第一層極性相反（下降邊緣 = 秒的開頭，量低電位寬度），
確認時間 80 → 40 ms（最短低電位 0.1 s），兩次下降隔 2 秒就補一個 `M`。Core 1 兩個解碼器同時餵，
畫面、統計頁第 8 行、記錄檔都依調諧點選一個；BPC 寫 `BPCLOG.TXT`。RAM 多約 200 B。

[15] 雜訊＋衰落的包絡、從幀中間開始：第 59 秒鎖定、22:50:00、時間戳差 14 ms；
[16] 68.5 kHz 載波經 DDC：鎖定 22:49:40、差 17 ms。第一次就全過。
